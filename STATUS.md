# Статус проекта НайдИИ

Короткая справка для быстрого старта в новой сессии (например, на другом компьютере) — что уже сделано,
где что лежит, что дальше. Полное ТЗ обсуждалось в чате и не хранится файлом в репозитории, за
исключением одной правки — см. раздел «Ожидает решения» ниже, она записана в отдельный файл.

## В работе — пивот на карточки услуг

**[`PIVOT_SERVICE_CARDS.md`](PIVOT_SERVICE_CARDS.md)** — 2026-08-22 пользователь прислал правку ТЗ:
главным объектом каталога должна стать карточка услуги (со стандартной автообложкой), а не профиль
специалиста. Открытый вопрос про нишу **закрыт**: ниша остаётся прежней — те же 10 AI-направлений
(`web/src/data/categories.ts`), список общих категорий в примере ТЗ (дизайн/видео/Excel и т.д.) был
только иллюстрацией структуры карточки, не расширением бизнеса.

**Первый срез реализован (2026-08-22):**
- PocketBase: миграция [`1755000016_service_cards_pivot.js`](pocketbase/pb_migrations/1755000016_service_cards_pivot.js)
  добавляет в `services` поля из карточки (category_id, tagline, tags, scope_label, revisions_included,
  price_type, preview_images), в `specialist_profiles` — completed_orders_count, в `promotions` —
  service_id (продвижение теперь может целиться в конкретную карточку, не только в профиль целиком).
  **Ещё не накатана на живой сервер** — там всё ещё старая схема, накатить через обычный
  git pull + перезапуск `pb-naidii.service`, когда в следующий раз будет доступ к SSH-консоли.
- Фронтенд, модель данных на два уровня (раздел 6 `PIVOT_SERVICE_CARDS.md`, реализовано 2026-08-22):
  **`ResultType`** — тип результата, сама плашка (одна на всех продавцов, как «Telegram Звёзды» у
  Playerok), и **`ServiceOffer`** — конкретное предложение специалиста по этому типу (цена/срок/теги).
  Каталог (`/services`, Топ-20 на главной) показывает плашки типов результата — цена «от» минимальной
  среди офферов, число исполнителей. Клик по плашке → `/services/{slug}` со списком предложений
  (`ServiceOfferRow`, продвигаемые/по рейтингу первыми), клик по предложению → профиль специалиста.
  42 типа результата, 44 оффера — у 2 типов по 2 конкурирующих предложения (добавлены 2 лёгких мок-
  специалиста, specialist-11/12, специально чтобы проверить сравнение "тот же товар — разные продавцы";
  остальные 40 типов пока с одним предложением). Карточка — не вытянутый вверх прямоугольник, а
  `aspect-[4/3]` обложка-доминанта (теперь настоящая сгенерированная картинка на всех 42, см. ниже —
  изначально был CSS-градиент по направлению как заглушка) + декоративные акценты, в духе Playerok.
- **Готово (2026-08-23): все 42 из 42 обложек сгенерированы и подключены.** Промпты —
  [`COVER_ART_PROMPTS.md`](COVER_ART_PROMPTS.md), единый визуальный стиль (не игровая эстетика
  Playerok — не подходит B2B-аудитории, обоснование в документе). Пользователь генерировал партиями
  через Qwen/др. и сохранял в `web/public/covers/{slug}.png` под точными именами из промптов; какие
  слаги уже имеют настоящую картинку — список в [`web/src/data/cover-manifest.ts`](web/src/data/cover-manifest.ts)
  (ведётся вручную, файлы не сканируются на лету — `mock-services.ts` используется и в клиентских
  компонентах, там нет `fs`). Первые 30 обложек (AI-агенты/RAG/оркестрация/чат-боты/голосовые
  агенты/AI-видео) вышли тускловатыми — для последних 12 (CRM-AI/промпт-инжиниринг/AI-аналитика)
  промпты переписаны на явно более яркие/насыщенные (`highly saturated`, `punchy poster-bright colors`,
  `NOT muted/pastel/washed-out/dull`). **Открытый пункт:** AI-агенты, No-code оркестрация и Чат-боты
  получились в одной сине-голубой гамме и плохо различимы рядом на сетке — see заметка в
  `COVER_ART_PROMPTS.md` под заголовком «Известная проблема: цвета направлений пересекаются» — возможно,
  захочется перегенерировать 1-2 из этих трёх более контрастным цветом, когда будет время визуально
  свериться по всей сетке `/services`.
- **Готово (2026-08-23): форма создания карточки услуги** —
  [`web/src/components/dashboard/ServiceCreationForm.tsx`](web/src/components/dashboard/ServiceCreationForm.tsx),
  вкладка «Услуги» в `/dashboard`. Каскад направление → подкатегория → тип результата (из существующего
  списка `mockResultTypes`, не свободный ввод названия — раздел 6 правки), с эскейпом «предложить свой
  тип на модерацию», если подходящего нет. Ограниченный набор полей предложения: цена (фикс./«от»), срок,
  правки (число или явно «без правок»), метки — только те, что специалист вправе проставить сам
  (`urgent`/`online`/`guaranteed`/`has_examples`; `verified`/`top` — знаки доверия от площадки, в форме
  недоступны), одна строка УТП, одна картинка-пример (загрузка через `URL.createObjectURL`, реального
  аплоада и авто-кадрирования/дуотон-наложения из раздела 4 правки ещё нет — это следующий шаг). Живой
  чек-лист автопроверки (раздел 8 правки) блокирует кнопку отправки, пока не выполнены все пункты,
  включая примитивный детектор контактов для ухода со сделки (regex на телефон/email/@telegram/t.me).
  Вкладка «Услуги» дашборда теперь читает реальные `mockServiceOffers` специалиста (общая модель с
  публичным `/services`), а не старое плоское поле `Specialist.services` — новые карточки существуют
  только в состоянии React (метка «На модерации»), сброс при перезагрузке, как и весь остальной кабинет.
  Проверено вручную в браузере (каскад, детектор контактов, блокировка кнопки, добавление в список).
- **Не сделано из этого среза:** `/specialists` и `/specialist/{slug}` не тронуты (профиль остаётся,
  просто больше не главный экран); PocketBase-схема ещё не разъединена под ResultType/ServiceOffer (пока
  только фронтенд-модель, миграция 1755000016 описывает старую 1:1 структуру); полная формула
  ранжирования (раздел 6 правки) — на моках упрощена до "продвигаемые сначала, потом по рейтингу";
  авто-кадрирование/дуотон-наложение загруженной картинки (сейчас просто показывается как есть).

## Что уже готово (на 2026-08-22)

**Backend (PocketBase)**
- Схема данных полностью описана миграциями в [`pocketbase/pb_migrations/`](pocketbase/pb_migrations/)
  — 14 коллекций, соответствуют ТЗ §11 (+ `categories`, добавлена сверх ТЗ для SEO-страниц из §13.1).
  Детали решений и известные грабли PocketBase 0.28 (fields нужно добавлять через
  `collection.fields.add()`, а не списком в конструкторе) — в [`pocketbase/README.md`](pocketbase/README.md).
- Развёрнут и работает на реальном сервере: Timeweb VPS `spb-3-vm-2v0g`, путь `/opt/naidii/pocketbase`,
  systemd-служба `pb-naidii.service`, порт `127.0.0.1:8093` (сервер общий с другими проектами — ПОТОК/
  DudergoFF, боты — там нет Docker, только Caddy + systemd, поэтому и здесь так же). С 2026-08-24 доступен
  публично на `https://pb.naidii.ru` (Caddy проксирует, `/_/` закрыт — 404 снаружи).
- Суперпользователь PocketBase создан (`admin@naidii.ru`, пароль знает только пользователь — не хранится
  в репозитории).
- Доступ сервера к GitHub — через отдельный deploy-ключ `~/.ssh/naidii_deploy` на самом сервере (не
  привязан к конкретному компьютеру-клиенту, работает откуда угодно по SSH на сервер).
- **Важный пробел, всплывший при ревью:** в `specialist_profiles` нет поля категории/направления —
  только `skills.category` (свободный текст, не связь). Понадобится новая миграция, когда будем
  привязывать специалистов к направлениям каталога по-настоящему (см. также `PIVOT_SERVICE_CARDS.md`).

**Frontend (Next.js)** — весь на моках, PocketBase ещё не доступен по интернету фронтенду (см. «Что не
готово»). **Живёт на настоящем домене (2026-08-24): https://naidii.ru** — задеплоен на тот же VPS, что и
PocketBase (`spb-3-vm-2v0g`), как обычный Next.js SSR-сервер (не статический экспорт), тем же способом,
что и PocketBase — systemd-служба `naidii-web.service`, `npm run start` на порту `127.0.0.1:3001`, Caddy
проксирует `naidii.ru`/`www.naidii.ru` на неё. `pb.naidii.ru` тоже поднят и смотрит на PocketBase
(порт 8093), `/_/` закрыт (404 снаружи) — в отличие от остальных сайтов на этом сервере, где админка
PocketBase открыта всем. Node.js 22 на сервере поставлен через NodeSource (раньше отсутствовал).
`web/next.config.ts` теперь поддерживает два режима сборки: `STATIC_EXPORT=true` (GitHub Actions,
статический экспорт для GitHub Pages) и обычный `npm run build` без этой переменной (SSR-сборка для VPS).
GitHub Pages (**https://butman76.github.io/naidii/**) при этом продолжает работать как параллельная
витрина — [`.github/workflows/deploy-web.yml`](.github/workflows/deploy-web.yml) на каждый push в `main`.

- `/` — главная: шапка, hero с поиском, сетка «Топ-20 услуг» (5×4 на десктопе, ТЗ §4.4, объект сетки
  сменился с профиля на карточку услуги в рамках пивота).
- `/services` — каталог карточек услуг: поиск, фильтр по направлению и меткам, сортировка.
- `/specialists` — каталог специалистов (вторичный, "уровень доверия") с поиском, фильтром по
  направлениям/навыкам, сортировкой.
- `/specialist/{slug}` — профиль специалиста; один из 48 моков (`specialist-5`, «Студия «Автоматика»»)
  показывает **премиум-версию профиля** (обложка, галерея, команда, сертификаты) — визуальный мокап
  максимального тарифа, флаг `premium` проставлен вручную в моках, к реальной оплате не привязан.
- `/categories`, `/category/{slug}` — 10 направлений (`web/src/data/categories.ts`), SEO-поля
  (title/description/H1/FAQ) на каждую, ТЗ §13.1.
- `/tariffs` — витрина 3 тарифов (Старт/Стандарт/Максимальный) по схеме `plans`, без оформления заказа.
- `/dashboard` — кабинет специалиста (Обзор/Профиль/Услуги/Заявки/Отзывы/Тариф), фейковый залогиненный
  пользователь, баннер «демо-режим».
- `/dashboard/customer` — кабинет заказчика (заявки/отзывы/избранное — избранное только визуально,
  в схеме БД ещё не реализовано).
- `/admin` — админ-панель: модерация профилей/отзывов, категории, тарифы, неизменяемый журнал действий.

Ни одна из кабинетных/админских страниц не защищена реальной авторизацией — это подчёркнуто баннером на
каждой. Кнопки типа «Написать», «Войти» — без обработчиков.

## Что не готово

- Домен `naidii.ru` теперь резолвится на VPS (`83.147.246.248`) — DNS переключён с бонусного shared-
  хостинга Timeweb (тот отдельный продукт, `hosting.timeweb.ru`, остался неиспользуемым, но уже оплачен
  до марта 2027 — можно пригодиться потом для чего-то ещё). `www.naidii.ru` тоже настроен.
- Автоматического резервного копирования БД (и теперь ещё и фронтенда) пока нет — как и у других
  проектов на этом сервере.
- Переключение фронтенда с моков на реальные запросы к PocketBase — теперь технически возможно (оба
  живут на одном сервере, домен есть), но ещё не сделано — фронтенд всё ещё читает `mock-*.ts`.
- Реальная оплата: схема (`orders`, `site_settings.payment_mode`) уже поддерживает ручной сценарий
  («перевёл → загрузил чек → админ подтвердил») без интеграции с платёжным шлюзом — можно стартовать на
  нём, не дожидаясь выбора и подключения конкретного эквайринга (`payment_provider` пока не выбран из
  перечисленных в схеме вариантов).
- **Пивот на карточки услуг** — первый срез сделан (см. раздел выше, включая форму создания карточки и
  все 42 обложки), но PocketBase-схема ещё не разъединена под модель ResultType/ServiceOffer (миграция
  1755000016 описывает старую 1:1 структуру), и часть разделов правки ТЗ (авто-проверка публикации,
  полная формула ранжирования) не реализована.

## Как продолжить с другого компьютера

```bash
git clone https://github.com/Butman76/naidii.git
cd naidii/web && npm install
```

Дальше можно `npm run dev` для локальной разработки. Доступ на сам сервер (SSH) не привязан к
компьютеру — нужны только реквизиты входа на `spb-3-vm-2v0g`, которые есть у пользователя.

Claude Code в этой папке при старте сессии сам подхватывает [`CLAUDE.md`](CLAUDE.md) в корне репозитория,
который указывает читать этот файл и `PIVOT_SERVICE_CARDS.md` — отдельно просить об этом не нужно.

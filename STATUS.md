# Статус проекта НайдИИ

Короткая справка для быстрого старта в новой сессии (например, на другом компьютере) — что уже сделано,
где что лежит, что дальше. Полное ТЗ обсуждалось в чате и не хранится файлом в репозитории, за
исключением одной правки — см. раздел «Ожидает решения» ниже, она записана в отдельный файл.

## Готово — страница «Как это работает» и «Не нашли то, что вам надо?» (2026-08-28)

По прямому запросу пользователя:

- **`/how-it-works`** — раньше ссылка в шапке вела в никуда (страницы не существовало вовсе).
  Теперь: верхний блок (~2/3 экрана) — яркое описание сути площадки (бизнес ищет
  исполнителей для AI-автоматизации, от частников до студий) + строка из 9
  цветных 3D-плашек направлений (тот же `getCategory3D()`, что на главной и
  `/categories`). Ниже — FAQ-туториал по группам (Регистрация / Как заказать
  услугу / Навигация по сайту / Если чего-то не хватает), честно описывает
  то, что реально работает сейчас (не Фазу B — переписки ещё нет, специалист
  связывается по контактам из заявки).
- **«Не нашли то, что вам надо?»** — новая вкладка в кабинете заказчика
  (`CustomerDashboard.tsx`). Текст идеи пишется в новую коллекцию
  `suggestions` (миграция
  [`1755000037_suggestions.js`](pocketbase/pb_migrations/1755000037_suggestions.js))
  и письмом уходит на `info@naidii.ru` через **новый для проекта** механизм —
  `pb_hooks/suggestions.pb.js` (до сих пор были только `pb_migrations`, хуков
  не было вообще).
  - **Хук протестирован локально до деплоя** (в этот раз, в отличие от
    истории с `MailerTemplate`, — специально скачал PocketBase 0.28.4,
    прогнал все миграции + хук на реальном сервере, создал тестового
    заказчика и запись `suggestions` через REST API). Результат: хук
    находит автора, читает `app.settings()`, собирает письмо как обычный
    JS-объект (без `new MailerMessage(...)` — по аналогии с уроком из
    `MailerTemplate`, что не все Mailer-типы существуют как глобальные
    конструкторы в JSVM) и вызывает `app.newMailClient().send(...)` —
    синтаксически всё отработало чисто, единственная ошибка была
    "failed to locate a sendmail executable path", то есть чисто из-за
    отсутствия настроенного SMTP на локальной тестовой машине. На проде SMTP
    уже настроен (тот же ящик `reg@naidii.ru`, что и для писем-подтверждений
    почты) — должно реально уйти.
  - **Не проверено:** существует ли сам ящик `info@naidii.ru` на Timeweb —
    если нет, письму физически некуда доставиться (это будет не ошибка
    хука, а отсутствие получателя). Стоит завести так же, как заводили
    `reg@naidii.ru`, если только `info@` ещё не существует.
  - Отправка идеи не ломается, даже если письмо не ушло — запись всё равно
    сохраняется в базе, письмо оборачивается в try/catch.

## В работе — «заказчик заказывает услугу» (начато 2026-08-27)

Стратегия (согласована с пользователем): без регистрации обеих сторон —
никакого взаимодействия вообще, гостевые заявки не разрешены. Переписка
между заказчиком и специалистом (не разовая форма), таймер среднего
времени ответа, email-уведомление специалисту (по галке в настройках) —
всё это отдельные следующие фазы, пока не сделаны. План:
- **Фаза A (сделано частично, 2026-08-27):** точка входа — кнопка «Заказать»
  на `/services/{slug}` (см. ниже), гейт на регистрацию, `leads.createRule`
  ужесточён. Ещё не сделано в Фазе A: такая же кнопка на `/specialist/{slug}`
  (профиль специалиста — сейчас там «Написать»/«Заказать» без обработчика).
- **Фаза B (не начата):** реальная переписка — новая коллекция
  `lead_messages`, вкладки «Заявки» в обоих кабинетах становятся тредом
  сообщений, а не списком на чтение.
- **Фаза C (не начата):** настоящее среднее время ответа (хук PocketBase на
  создание сообщения, скользящее среднее в `specialist_profiles`) — заменит
  сегодняшний самозаявленный `response_time`.
- **Фаза D (не начата):** email специалисту о новом сообщении, только если
  включена галка в настройках профиля (хук + уже настроенный SMTP).
- **Фаза E:** платежи — сознательно не в этот заход.

Что уже сделано по Фазе A:
- `/services/{slug}` — карточки предложений (`ServiceOfferRow.tsx`)
  переделаны из вытянутых строк в компактную сетку (по просьбе — «больше
  помещается»), сама страница расширена до `max-w-6xl`.
- Новый `OrderButton.tsx` (переиспользуемый) — не залогинен → показывает
  «Нужна регистрация» со ссылками на `/register`/`/login`, не создавая
  ничего; залогинен как `customer` → реально создаёт запись `leads`
  (`specialist_profile_id`, `customer_id`, текст с названием услуги,
  `status: "new"`). Проверено в браузере: гейт показывается корректно.
  Пока это разовая заявка (Фаза B заменит/расширит её на тред сообщений).
- `ServiceOffer` (тип, `types/service-card.ts`) — добавлено поле
  `specialistProfileId` (реальный id записи `specialist_profiles`, не
  слаг) — понадобилось, чтобы было что положить в `leads.
  specialist_profile_id`; заполнено в `catalog.ts` и `dashboard.ts`.
- Миграция
  [`1755000035_leads_require_registration.js`](pocketbase/pb_migrations/1755000035_leads_require_registration.js)
  — `leads.createRule` был публичным (`""`, гостевые заявки по ТЗ §7.1),
  теперь требует `role = "customer"` и `customer_id = @request.auth.id`
  (нельзя оставить заявку от чужого имени). Это прямое противоречие
  исходному ТЗ — пользователь explicitly отменил тот пункт.
- **Визуальная доводка Фазы A (2026-08-27, тот же день):** по обратной связи
  пользователя со скриншота —
  - Кнопка «Заказать» после успешной отправки не текст блёклого цвета, а
    настоящий 3D-переворот (flip-card, новые классы `.order-flip-*` в
    `globals.css`, по тому же принципу, что уже был `.plate-3d`) — на месте
    кнопки появляется яркая 3D-плашка в цвет направления услуги
    (`getCategory3D()`) с текстом подтверждения.
  - `leads` получил новое поле `category_slug` (миграция
    [`1755000036_leads_category.js`](pocketbase/pb_migrations/1755000036_leads_category.js))
    — строка, не строгая связь (специально не стали городить `service_id`
    ради этого), проставляется на фронте в момент отправки заявки
    (`OrderButton.tsx` уже знает направление услуги).
  - Обе вкладки «Заявки» (кабинет специалиста и кабинет заказчика) —
    квадратная сетка вместо списка строк, у каждой карточки цветной
    кружок + мягкая рамка/фон в цвет направления (`getCategoryStyle`/
    `getCategoryAccent`), тот же язык, что уже был у вкладки «Услуги».
  - **Не проверено скриншотом** — сама 3D-анимация переворота: попытка
    проверить через `getComputedStyle` в этой headless-среде показала
    identity-матрицу даже для инлайнового `!important transform`, при
    этом изолированный `rotateY` в том же браузере считается верно — похоже
    на известное ограничение среды (сообщение "страница не компонует
    кадры, пока панель не отображается" уже встречалось раньше в этой
    сессии), а не баг в CSS. Стоит один раз глянуть вживую после деплоя.

## В работе — переход с моков на живые данные (начато 2026-08-24)

После деплоя на настоящий домен решили переводить весь сайт на реальные запросы к PocketBase вместо
`web/src/data/mock-*.ts`, по частям, без остановки между этапами.

**Сделано:**
- PocketBase-схема разъединена под модель ResultType/ServiceOffer (миграции 1755000017/1755000018 —
  подробности в разделе пивота ниже) и **наполнена реальным содержимым** (миграция 1755000019): 10
  категорий, 42 типа результата, 11 демо-специалистов (аккаунты вида `specialist-N@seed.naidii.ru`,
  общий временный пароль, явно помечены как сид-данные, не настоящие люди), 44 предложения, 8 активных
  продвижений. Сгенерирована из тех же `web/src/data/mock-*.ts` через одноразовый скрипт (не переписана
  руками) — так исключены опечатки, но найдена и исправлена одна реальная нестыковка в самих моках:
  рейтинг специалиста хранился в двух файлах с разными значениями (общая формула по индексу в
  `mock-specialists.ts` против вручную заданного в `mock-services.ts` — при живых данных рейтинг стал
  ровно одним полем на специалиста, что и вскрыло расхождение).
- Найден и исправлен попутный баг схемы: числовое поле `top_position` у непривязанного к сетке
  продвижения по умолчанию хранится как `0`, а не `NULL`, из-за чего уникальный индекс падал уже на
  второй такой записи (1755000018_fix_promotions_position_index.js).
- Все три миграции перед деплоем на сервер проверены **локально** — скачан Windows-бинарник PocketBase
  0.28.4 именно для этого, прогнан на копии миграций, проверены количества записей и раскрытие связей
  через API, только потом накатано на боевой сервер. То же самое стоит делать и для будущих миграций,
  особенно объёмных сидов — дешевле поймать ошибку локально, чем гонять правки через SSH-релей.
- Фронтенд: `web/src/lib/pocketbase.ts` (клиент на `https://pb.naidii.ru` — этот же адрес одинаково
  работает и с VPS, и с любого компьютера разработки) и `web/src/lib/catalog.ts` (запрос + маппинг записей
  БД в те же типы `ResultType`/`ServiceOffer`, что и раньше использовали моки, поэтому компоненты каталога
  переписывать не пришлось). **`/`, `/services`, `/services/{slug}` теперь на живых данных**, проверено и
  локально, и на настоящем сайте.
- `/services/[slug]/page.tsx`'s `generateStaticParams` тоже дергает живые данные — значит и статическая
  сборка для GitHub Pages (`STATIC_EXPORT=true`) продолжает работать, просто данные в неё попадают на
  этапе сборки в CI, а не как раньше — из моков.
- **`/specialists`, `/specialist/{slug}`, `/categories`, `/category/{slug}` тоже на живых данных**
  (`web/src/lib/specialists.ts`) — проверено на сайте: 11 специалистов, их профили с реальным списком
  услуг (не моковым `Specialist.services`, а живыми предложениями из `services`/`result_types`), число
  специалистов на карточке направления. Два честных упрощения против моков, а не баги: теги навыков
  пустые (`specialist_skills` ещё не наполнен) вместо выдуманных, и фильтр по навыкам в каталоге убран —
  фильтровать пока не по чему; отзывы тоже пустые (коллекция `reviews` без данных), вместо придуманных
  демо-отзывов. Заодно перевёл на живые данные и цифры на главной (`TrustStats.tsx`) — они рядом с
  теперь-живой сеткой карточек, старые моковые числа рядом с реальными выглядели бы странно.

- **Настоящая регистрация и вход (2026-08-24)** — `/register` (специалист/заказчик), `/login`, оба через
  `pbClient.collection("users")` (`web/src/lib/auth-client.ts`, `web/src/lib/use-auth.ts`). Регистрация
  специалиста сразу создаёт `specialist_profiles` (`profile_status: "pending"`, `slug` = id пользователя —
  гарантированно уникален). Оба кабинета (`/dashboard`, `/dashboard/customer`) теперь закрыты
  `RequireAuth` — реально проверяют сессию PocketBase и роль, не пускают без входа/с чужой ролью (раньше
  были открыты кому угодно за демо-баннером). Шапка (`AuthStatus.tsx`) показывает реальное имя вошедшего и
  кнопку выхода вместо статичной ссылки «Войти». Проверено вручную в браузере целиком: регистрация
  специалиста → авто-вход → запись в БД с `pending` → кабинет → выход → редирект неавторизованного с
  `/dashboard` на `/login` → повторный вход; отдельно — регистрация заказчика уходит в
  `/dashboard/customer` без создания `specialist_profiles`.
- **Содержимое кабинетов на живых данных (2026-08-24)** — исправлен баг, найденный пользователем при
  первой же ручной проверке: вход был настоящим, но внутри кабинета оба показывали один и тот же
  захардкоженный мок (специалист «Алексей Морозов» — реальный пользователь, зарегистрировавшийся как
  «Марат», видел в своём кабинете чужое имя и чужие данные). `web/src/lib/dashboard.ts` —
  `fetchOwnSpecialistDashboard`/`fetchOwnCustomerDashboard`, запросы от имени вошедшего
  (`specialist_profiles`/`services`/`leads`/`reviews`/`cases`, отфильтрованные по своему `user_id`/
  `specialist_profile_id`/`customer_id`). Для новых профилей (ещё без данных) честно показываются нули и
  пустые списки («У вас пока нет заявок», «Отзывов пока нет») — это не баг, а правда, а не выдуманные
  цифры как раньше. Заодно убран баннер «Демо-режим», который стал прямой ложью после того, как вход
  реально заработал. Проверено вручную на обоих тестовых аккаунтах — специалист и заказчик видят своё
  собственное (пустое) состояние, не чужое.
- **Фаза 1 плана «от регистрации до модерации» — карточки услуг реально сохраняются (2026-08-25)** —
  раньше `ServiceCreationForm.tsx` писала оффер только в React-state (колбэк `onCreated(offer)`),
  в PocketBase ничего не попадало, вкладка «Услуги» сбрасывалась при перезагрузке. Теперь:
  - Список типов результата в форме — живой (`pb.collection('result_types').getFullList(...)`), не
    `mockResultTypes`.
  - По сабмиту — настоящий `pb.collection('services').create({...})` с полями по факту схемы
    (`result_type_id`, `specialist_profile_id`, `tagline`, `price_type`, `price_from`, `duration_from`,
    `revisions_included`, `tags`, `active: true`). Отдельной модерации на уровне карточки нет — видимость
    целиком зависит от `specialist_profiles.profile_status = "published"` (уже было в `listRule`
    коллекции `services`), так что после публикации профиля все его активные карточки видны сразу.
  - **«Предложить свой тип услуги»** (эскейпхетч в форме, когда подходящего типа нет) теперь тоже
    реальный, не заглушка: специалист вводит название + категорию (уже была в форме) + подробное
    описание (новое поле) + свою цену (как и для обычных типов — цену всегда назначает исполнитель,
    ResultType её не хранит). Отправка создаёт настоящую запись `result_types` со
    `status: "pending"` — новая миграция
    [`1755000021_result_type_submissions.js`](pocketbase/pb_migrations/1755000021_result_type_submissions.js)
    добавила в `result_types` поля `description`/`status`/`created_by` и переписала правила доступа:
    публично видны только `approved`, автор видит свою заявку на модерации, admin/moderator — всё.
    Существующим 42 типам при миграции проставлен `status: "approved"` (иначе они бы пропали из
    публичного каталога — до миграции такого поля не было вообще). Специально проверил, что
    `catalog.ts` не нужно было трогать: его код уже отбрасывал офферы, чьи `result_type_id` не
    раскрылись через `expand` (было написано на будущее, до этой фичи expand просто никогда не был
    пустым) — ровно то поведение, которое нужно, чтобы неодобренный тип не протёк в публичный каталог.
  - `SpecialistDashboardClient.tsx` — рефакторинг: `refresh()` вынесен в переиспользуемый колбэк,
    после реального сохранения кабинет перечитывает данные с сервера вместо локального
    `pendingOffers`-стейта (удалён).
  - **Найден и исправлен баг сразу после первого деплоя на прод:** `SpecialistDashboardClient.tsx`
    при рефакторинге под `refresh()` потерял защиту от лишнего повторного запроса (`useAuth()` отдаёт
    новый объект `user` сразу после монтирования — та же личность, новая ссылка — из-за чего эффект
    перезапускался, PocketBase сам отменял первый запрос, а это ошибочно трактовалось как настоящая
    ошибка). Результат — кабинет специалиста показывал «Не удалось загрузить профиль» почти всегда,
    поймано пользователем вживую на подтверждённом «Анчоус». Исправлено (зависимость на `user?.id`
    вместо объекта `user`, `err.isAbort` игнорируется в catch), задеплоено, подтверждено — кабинет
    снова открывается.
  - **Статус на конец сессии 2026-08-25 (ночь):** пользователь тестирует вживую на «Анчоус» —
    дошёл до формы создания карточки, чек-лист автопроверки реагирует правильно (не давал
    опубликовать, пока не выбран конкретный тип результата из списка — это ожидаемое поведение формы,
    не баг). Сам факт успешной публикации карточки (и отдельно — сценарий «предложить свой тип») ещё
    не подтверждён до конца — это первое, с чего стоит продолжить в следующей сессии.
  - **Публикация подтверждена (2026-08-27):** «Анчоус» реально опубликовал 3 карточки, они видны в
    его кабинете. Пользователь попросил визуально доработать кабинет по итогам первого взгляда:
    - Услуги теперь сгруппированы по направлению (не вперемешку) и оформлены компактной сеткой
      квадратных плашек вместо длинных строк — влезает заметно больше на экран.
    - У каждой карточки — цветная плашка направления (градиент в цвет категории, без эмодзи — просили
      убрать) вместо простого текста.
    - Профиль-таб — теперь с рабочей формой редактирования (заголовок/краткое/полное описание, пишет

  проектов на этом сервере.
- Переключение фронтенда с моков на реальные запросы к PocketBase — теперь технически возможно (оба
  живут на одном сервере, домен есть), но ещё не сделано — фронтенд всё ещё читает `mock-*.ts`.
- Реальная оплата: схема (`orders`, `site_settings.payment_mode`) уже поддерживает ручной сценарий
  («перевёл → загрузил чек → админ подтвердил») без интеграции с платёжным шлюзом — можно стартовать на
  нём, не дожидаясь выбора и подключения конкретного эквайринга (`payment_provider` пока не выбран из
  перечисленных в схеме вариантов).
- **Пивот на карточки услуг** — первый срез сделан (см. раздел выше, включая форму создания карточки и
  все 42 обложки), но PocketBase-схема ещё не разъединена под модель ResultType/ServiceOffer (миграция
  1755000016 описывает старую 1:1 структуру), и часть разделов правки ТЗ (авто-проверка публикации,
  полная формула ранжирования) не реализована.

## Как продолжить с другого компьютера

```bash
git clone https://github.com/Butman76/naidii.git
cd naidii/web && npm install
```

Дальше можно `npm run dev` для локальной разработки. Доступ на сам сервер (SSH) не привязан к
компьютеру — нужны только реквизиты входа на `spb-3-vm-2v0g`, которые есть у пользователя.

Claude Code в этой папке при старте сессии сам подхватывает [`CLAUDE.md`](CLAUDE.md) в корне репозитория,
который указывает читать этот файл и `PIVOT_SERVICE_CARDS.md` — отдельно просить об этом не нужно.

# PocketBase-схема НайдИИ

Схема данных из ТЗ §11 реализована как JS-миграции PocketBase (`pb_migrations/`) —
это код, а не ручная настройка через `/_/`, поэтому она версионируется в
репозитории и применяется автоматически при каждом старте PocketBase.

Миграции написаны под синтаксис PocketBase **v0.23+** (объекты `Field`,
`Collection`, метод `app.save(...)`). Точную версию нужно сверить при первом
реальном запуске — API миграций менялся между релизами, и без живого
инстанса эти файлы не были прогнаны.

## Как применить

1. Положить бинарник/образ PocketBase так, чтобы папка `pb_migrations` лежала
   рядом с `pb_data` (при Docker Compose — смонтировать этот каталог в
   `/pb/pb_migrations`).
2. При старте PocketBase сам находит новые файлы в `pb_migrations` и
   применяет их по возрастанию имени файла (это и есть порядок из списка
   ниже — от него нельзя отступать, т.к. поздние коллекции ссылаются на
   `id` более ранних через `findCollectionByNameOrId`).
3. Первого суперпользователя (для `/_/`, который должен быть закрыт от
   публичного доступа согласно §3.1) создать через
   `pocketbase superuser create <email> <password>` — это отдельная сущность
   от бизнес-роли `users.role = "admin"`, см. ниже.

## Осознанные решения и отклонения от буквы ТЗ

ТЗ в §11 даёт только имена полей, без типов и правил доступа. Ниже — как
это интерпретировано и что добавлено сверх текста:

- **`categories`** — отдельная коллекция, не указанная в §11, но без неё
  невозможно выполнить §13.1 (уникальные title/description/H1/FAQ на
  каждую `/category/{slug}` страницу, редактируемые без правки кода). Поле
  `skills.category` при этом оставлено как есть — простой текст, а не связь,
  как буквально написано в §11.3.
- **`plans`** — добавлены `trial_days`, `discount_percent`, `sort_order`,
  `description`: они явно требуются в §8.5 ("пробный период", "размер
  скидки" настраиваются в тарифе), просто не попали в сокращённый список
  полей §11.8.
- **Два разных "администратора".** PocketBase-суперпользователь (доступ к
  `/_/`) и бизнес-роль `users.role = "admin"` (доступ к кастомной
  `/admin`-панели на Next.js) — разные вещи. Все правила доступа коллекций
  ниже опираются на `@request.auth.role`, т.к. `/admin` предполагается
  логиниться через обычную `users`-коллекцию (роли `admin`/`moderator`
  описаны в §7.4–7.5), а не через суперпользователя PocketBase.
- **`orders.status` и суммы недоступны на запись клиенту.** Правило
  `updateRule` для `orders` — только `admin`. Это значит, что действие
  "Я оплатил" / загрузка чека (§10.2) должно идти через серверный
  Next.js API-роут с собственным сервис-аккаунтом, а не прямой записью из
  браузера — иначе покупатель мог бы сам выставить себе статус "Оплачен".
  То же самое будет для `POST /api/payments/alfa/callback` на Этапе 2.
- **`admin_logs` — только на добавление.** `updateRule`/`deleteRule` = `null`,
  т.е. запись нельзя изменить или удалить даже с ролью `admin` через API —
  только через суперпользователя PocketBase напрямую в БД. Это соответствует
  требованию журнала действий в §8.6 (неизменяемый аудит).
- **`site_settings`** — в PocketBase нет типа "singleton"-коллекции, поэтому
  это обычная коллекция с одной засеянной строкой; поддержание "ровно одна
  запись" — ответственность админ-панели (открывать существующую запись на
  редактирование, не давать создавать вторую).
- **Уникальность позиции в топ‑20** обеспечена частичным уникальным
  индексом на `promotions.top_position` (только для `status = "active"`) —
  это то, что не даёт двум активным продвижениям занять одно и то же место
  в сетке 5×4 из §4.4/§8.3.

## Что дальше по схеме

Не хватает для полноты (можно добавить следующим шагом, по запросу):
- коллекция для внутренних уведомлений личного кабинета (§12.1 "Уведомления
  внутри личного кабинета" не описаны как отдельная сущность в §11);
- избранное у заказчика (§7.2 "сохранять специалистов в избранное") — в
  §11 не описано, это Этап 3 по roadmap (§14), но потребует join-таблицы
  `favorites` уже на MVP, если фичу решат не откладывать.
